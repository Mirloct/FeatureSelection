Resumen

La nueva etapa corre después de validar la llave del panel y antes del primer diagnóstico estadístico. Por ello, las features creadas no reciben trato preferencial: entran como candidatas normales y las reglas existentes pueden retirarlas por exceso de nulos, falta de relevancia o redundancia.

El KDE se usa exclusivamente como generador de variables de rareza. Para una observación del mes t, la referencia contiene solo meses anteriores y el perfil comparable configurado. Cada conducta se procesa por separado.

Metadata

Outputs: DataFrame enriquecido, catálogo/estabilidad de features y CSV numérico en ConfigPipeline.ruta_matriz_anomalias_efectiva.

Supuestos y decisiones

  • La granularidad es exactamente una fila por entidad y mes; los duplicados siguen siendo bloqueantes.
  • Las conductas deben ser numéricas después de la tipificación.
  • Un perfil con menos de min_group_size observaciones históricas deja la feature KDE en nulo. No se mezcla silenciosamente con la población global.
  • Los nulos iniciales son esperados: representan falta real de historia. La fase univariada decide si su cobertura total basta.
  • La matriz preparada no entrena un VAE ni convierte KDE en el modelo final; establece un insumo sin fuga para modelos posteriores.

Activación correcta

No active solamente el flag con los nombres de ejemplo. Primero configure columnas que existan en el panel y luego encienda la rama. El orden correcto es el siguiente.

1. Declare la granularidad y el archivo

entradas:
  ruta_dataset: "data/mi_panel.csv"
  columna_id: "customer_id"
  columna_tiempo: "month"
  columna_target: "fraud_flag"  # opcional: puede no existir en el archivo

2. Declare contexto y conductas reales

feature_engineering:
  usar_feature_engineering: true
  context_vars: ["age_group", "job_position"]
  behavior_vars: ["credit_count", "credit_amount", "account_balance"]
  incluir_context_vars_en_seleccion: false
  kernel_type: "gaussian"
  reference_mode: "joint_and_marginal"
  min_group_size: 100
  min_personal_history: 6
  bandwidth_method: "time_safe_cv"
  temporal_windows: [3, 6, 12]
  epsilon: 1.0e-8
  preparar_modelos_anomalia: true
  meses_holdout_anomalia: 3
  • context_vars: columnas que definen la población comparable; pueden ser categóricas o numéricas discretas.
  • behavior_vars: medidas mensuales que se evalúan una por una; deben quedar numéricas después de la tipificación.
  • incluir_context_vars_en_seleccion: false: opción recomendada para que atributos de perfil no lleguen directamente al detector.

3. Ejecute por una de estas dos vías

Activación persistente en YAML — si ya dejó usar_feature_engineering: true:

py run_pipeline.py --config config.yaml

Activación solo para una corrida — deje el interruptor en false y sobrescríbalo por CLI:

py run_pipeline.py --config config.yaml --usar-feature-engineering true

El flag de CLI solo cambia el interruptor. context_vars, behavior_vars y los demás parámetros continúan leyéndose desde el YAML.

4. Confirme la activación

  • La barra de progreso debe mostrar FE - Temporales y KDE condicional antes de Fase 0.
  • La bitácora debe contener las hojas 01e_FE_Catalogo, 01f_FE_Estabilidad, 01g_FE_Ablacion y 01h_Prep_IF_VAE.
  • Si preparar_modelos_anomalia: true, se crea el CSV con sufijo _matriz_anomalias.csv.

Validaciones previas y errores esperables

CondiciónResultado
Falta una variable configuradaSe detiene y lista las columnas faltantes.
Una conducta no es numéricaSe detiene antes de calcular temporales/KDE.
La llave entidad × mes está duplicadaLa validación estructural bloquea la corrida.
Hay pocos datos históricos en un perfilLa feature KDE queda nula hasta alcanzar min_group_size; no se usa una población global oculta.
No hay más meses que el holdout configuradoNo se exporta una matriz inválida; se informa que debe reducirse meses_holdout_anomalia o aportar más historia.

También se aceptan los alias id_col, time_col, target_col y random_state. Internamente se normalizan a la configuración canónica del proyecto.
